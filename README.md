## Описание
**Payments Service** — микросервис асинхронной обработки платежей, реализующий Clean Architecture. Он обеспечивает надежную доставку уведомлений клиентам (webhooks) с гарантией **at-least-once** и полной защитой от дубликатов на стороне потребителя (**идемпотентный consumer**).

Основные проектные решения:
- **Два механизма повторов**: Transactional Outbox (надежная публикация в брокер) и лестница TTL-очередей RabbitMQ (эффективная обработка временных сбоев на стороне клиента).
- **Гарантированная атомарность**: Сохранение платежа и события публикации выполняется в одной транзакции БД, что исключает потерю сообщений.
- **Идемпотентность**: Детерминированная проверка на уровне API (через Idempotency-Key и хэш запроса) и бизнес-логики (проверка состояния доставки вебхука).

## Запуск
### Требования
- Python 3.12+
- Docker Desktop
- Makefile (рекомендуется для удобства управления)

### Быстрый старт
```bash
# Клонируем проект
git clone https://github.com/RansonDev/payment-service.git
# Создаем .env
cp .env.example .env
# Перейти в директорию проекта
cd payments_service
# Запустить всё окружение (API, Воркеры, БД, RabbitMQ, Webhook-Echo)
docker compose up -d
docker compose ps
# Можно запустить через make 
make docker-up
# Справочные материалы по make ниже
```
> **Важно**: Сервис станет доступен (статус `healthy`), как только запустятся база данных и брокер (обычно 10-20 секунд).

- **Документация (Swagger)**: http://127.0.0.1:8000/api/docs
- **Тестовый сервер вебхуков**: `docker compose logs webhook-echo -f`

### Управление через Makefile
- `make docker-up` — запуск всех сервисов и автоматическое применение миграций.
- `make docker-down` — остановка и удаление контейнеров.
- `make check` — запуск линтеров (ruff, mypy) и модульных тестов.
- `make test-all` — запуск полного цикла тестов (unit + integration).
- `make logs` — просмотр логов всех компонентов в реальном времени.

### Демонстрация сценария
1. **Проверка готовности**: Убедитесь, что сервис запустился (отвечает `ok`):
```bash
curl http://127.0.0.1:8000/api/health
```
2. **Создание платежа**:
```bash
curl -X POST http://127.0.0.1:8000/api/payments \
  -H "Content-Type: application/json" \
  -H "X-API-Key: test-api-key-12345" \
  -H "Idempotency-Key: demo-unique-key-001" \
  -d '{"amount": 150.00, "currency": "RUB", "description": "Оплата заказа", "webhook_url": "http://webhook-echo:8080/hook"}'
```
3. **Проверка идемпотентности**: Повторный запрос с тем же `Idempotency-Key` вернет тот же `payment_id`. Изменение тела запроса при том же ключе вернет `409 Conflict`.
4. **Результат**: В логах `webhook-echo` появится JSON-уведомление о смене статуса платежа на `succeeded` или `failed`.

## Архитектура
Проект строго следует принципам Clean Architecture: **Domain** (сущности), **Application** (сценарии), **Infrastructure** (БД, RabbitMQ, HTTP) и **Presentation** (FastAPI).

### Схема потоков
```
[Client] -> POST /payments -> [API] -> (DB: Payment + Outbox)
                                 |
[Outbox Publisher] <- (SKIP LOCKED) <- [DB]
       | (Publisher Confirms)
[RabbitMQ] -> [Consumer] -> [Payment Gateway Emulator] -> [DB: Status Update]
                                 |
                          [Webhook Sender] -> [Client Webhook]
```

### Критичные инварианты
- **Атомарность Outbox**: Вставка платежа и сообщения происходит строго в одной транзакции через Unit of Work.
- **Гарантия публикации**: Событие отмечается как `published` в БД только после получения подтверждения (ACK) от RabbitMQ.
- **Надежность воркеров**: Использование `FOR UPDATE SKIP LOCKED` позволяет горизонтально масштабировать `Outbox Publisher` без риска дублирования или блокировок.
- **Retry Ladder**: Если вебхук не доставлен, сообщение проходит через очереди `retry.1` (5с), `retry.2` (10с), `retry.3` (20с) и, в случае окончательного сбоя, попадает в `payments.dlq`.

### Транспортный слой
Техническое задание предполагает использование FastStream для работы с RabbitMQ. В проекте применяется `aio-pika` напрямую. Основания для отклонения:

1. **Ограничения FastStream**: Фреймворк не реализует повторные попытки и отложенную доставку. Это заявленная позиция авторов: фреймворк не берёт на себя решения, относящиеся к архитектуре приложения. Параметр `retry` у подписчика выполняет `nack(requeue=True)` без задержки и без сохранения счётчика попыток между перезапусками процесса, что не удовлетворяет требованию трёх попыток с экспоненциальной задержкой.
2. **Конфликт жизненного цикла**: Фреймворк задаёт собственную модель жизненного цикла приложения и внедрения зависимостей, что конфликтует с принятой в проекте схемой на основе **Dishka**.

Требования 5 и 6 технического задания при использовании FastStream всё равно потребовали бы самостоятельной реализации.

#### Заимствованные компоненты
Из исходного кода FastStream 0.7.5 и `faststream-outbox` перенесены и адаптированы отдельные компоненты работы с брокером и хранилищем.

| Пакет | Источник | Содержание |
|---|---|---|
| `infrastructures/broker/aio_pika` | FastStream 0.7.5, Apache-2.0 | Декларация топологии с кешированием по хешу схемы. Продюсер с publisher confirms и passive-объявлением обменников. Политики подтверждения сообщений с защитой от повторного ack. |
| `infrastructures/outbox` | faststream-outbox, MIT | Выборка событий с `FOR UPDATE SKIP LOCKED`. Стратегии экспоненциальной задержки с джиттером и ограничением. |
| `infrastructures/context` | FastStream 0.7.5, Apache-2.0 | Хранилище контекста на `contextvars` и фильтр логирования для сквозного `trace_id`. |

Внесённые изменения зафиксированы в заголовке каждого модуля с указанием исходного файла и перечнем отличий.

Существенное отклонение от оригинала допущено в `infrastructures/outbox`: модель аренды строки (`acquired_token` с истечением по TTL) заменена на блокировку строки в рамках транзакции. Аренда необходима, когда захват строки и её обработка разнесены по разным транзакциям. В данном проекте публикация события выполняется за миллисекунды, транзакция удерживается на всё время операции, и освобождение блокировки при аварийном завершении процесса происходит автоматически.

#### Реализовано самостоятельно
Outbox-паттерн в связке с бизнес-транзакцией, лестница retry-очередей с dead-letter маршрутизацией и перевод сообщений в DLQ после исчерпания попыток в перечисленных библиотеках отсутствуют и реализованы в рамках проекта.

## Справочник API
Доступен интерактивный UI: http://127.0.0.1:8000/api/docs

- **POST /api/payments**: Регистрация платежа. Требует заголовки `X-API-Key` и `Idempotency-Key`. Возвращает `202 Accepted`.
- **GET /api/payments/{id}**: Получение полной информации о платеже и статусе доставки вебхука.
- **GET /api/health**: Проверка работоспособности компонентов (Health check).

## Структура проекта
```
src/payments_service/
├── domain/          # Чистая бизнес-логика (Entities, Value Objects)
├── application/     # Сценарии (Use Cases) и интерфейсы (Protocols)
├── infrastructures/ # Реализации: DB (SQLAlchemy 2.0), Broker (aio-pika), Gateway, Outbox
├── presentation/    # FastAPI Controllers, Schemas, Middlewares
├── workers/         # Фоновые процессы: Consumer, OutboxPublisher
└── config/          # Конфигурация, логирование и DI (Dishka)
```
**Зависимости**: Домен не зависит от внешних библиотек и других слоев. Направление импортов: `Presentation -> Application -> Domain`.

## Ограничения
### Известные особенности
- **Outbox Publisher**: Лимит попыток публикации в брокер не ограничен (retry до победного); обеспечивает корректную работу при длительной недоступности RabbitMQ.
- **Безопасность**: Вебхуки отправляются без криптографической подписи; для защиты рекомендуется ограничение доступа по IP.
- **Эмуляция шлюза**: Вместо внешней интеграции используется эмулятор с настраиваемым шансом успеха (`GATEWAY_SUCCESS_RATE`).
- **Мониторинг**: Management UI RabbitMQ доступен по адресу http://127.0.0.1:15672 (логин/пароль: `guest/guest`).

### Диагностика
- **Статус сервисов**: `docker compose ps` (убедитесь, что все контейнеры в статусе `Up` или `healthy`).
- **Просмотр логов**: `docker compose logs -f [app|consumer|outbox-publisher]`
- **Проверка инвариантов**: В корне проекта доступен `Makefile` с командами проверки состояния.
- **Windows**: Скрипты `entrypoint.sh` должны иметь LF окончания строк. При отсутствии `make` используйте прямые вызовы `docker compose`.
- **Сигналы**: На Windows вместо `loop.add_signal_handler` используется `signal.signal` для корректного завершения воркеров.
